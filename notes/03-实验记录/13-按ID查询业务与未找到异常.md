# 按 ID 查询业务与未找到异常

## 本轮改动

- UserService 接口新增 UserResponse findById(Long id)。
- UserServiceImpl 实现查询与错误判断。
- GlobalExceptionHandler 为 USER_NOT_FOUND 映射404，为业务 INVALID_ARGUMENT 映射400。
- 不新增GET入口，不修改Postman集合，不重启已有POST服务。

## 执行步骤

1. 检查 id 是否为 null 或小于等于0，不合法则抛 INVALID_ARGUMENT。
2. 调用已有 UserMapper.findById 查询数据库。
3. 没有记录时，Mapper返回null；Service把它解释为 USER_NOT_FOUND，而不是直接返回空的成功响应。
4. 查询成功时，将User转换为UserResponse。

`id == null || id <= 0` 使用短路或：左边为true时不再计算右边，避免null参与自动拆箱比较。
本方法只有一次SELECT，本阶段没有额外增加@Transactional；需要一致地读取多次或跨步骤操作时再讨论事务边界。

## 为什么由业务层解释未找到

Mapper只描述查询结果。普通查询找不到用户是404业务含义；“刚插入后却查不到”在创建流程中仍是内部异常，不能直接混为同一情形。
Service抛业务异常，全局异常处理器决定HTTP状态和统一响应，SQL中不写HTTP逻辑。

## 实际验证

Maven compile通过，在新的非Web Spring上下文中通过UserService接口调用，查询ID4、6、10均成功，用户名与数据库一致且创建时间非空。

| 输入 | 业务结果 | 处理器方法返回状态 |
| --- | --- | --- |
| 4、6、10 | UserResponse | 本轮未接HTTP成功响应 |
| Long.MAX_VALUE | USER_NOT_FOUND | 404 |
| null、0、-1 | INVALID_ARGUMENT | 400 |

错误状态通过调用真实全局处理器方法验证，不是正式GET请求验证。前后记录总数一致，本次观察为5条；没有新增、删除或修改数据。
